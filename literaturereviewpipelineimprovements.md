# Literature Review Pipeline Improvements

## The full corpus of searched papers is generated but never shown — only the 3 papers cited in the summary reach the UI

**Status:** Open
**Found:** 2026-07-19, right after wiring up the structured `literature.json` schema (decision/assessment/papers/conclusion) and confirming it renders correctly end-to-end.

**Problem:** The Literature stage's real backend search does far more work than the UI currently surfaces. `denario/langgraph_agents/literature.py`'s `semantic_scholar()` node calls the real Semantic Scholar API across multiple query-refinement rounds, and logs every paper it actually pulled back — not just the ones the LLM chose to cite in its final summary — to two files per project:

- `input_files/literature.log` — one JSON block per search round (`Reason` / `Decision` / `Query`) interleaved with the numbered paper listings for that round.
- `input_files/papers_processed.log` — every paper the search turned up, each as a `N. Title (year)\nAuthors: ...\nAbstract: ...\nURL: ...\n[optional pdf: ...]` block.

Confirmed on real project `90fa5f38-37fb-4cea-87ba-0f3bfbe7092f`: the search ran **3 query-refinement rounds** and turned up **43 distinct papers with full title/authors/abstract/URL**, but the final `literature.md` (and now `literature.json`) only ever surfaces the **3 papers** the LLM chose to compare against in its novelty summary. The other 40 — including full abstracts, author lists, and links — are written to disk and then never read again by anything.

**Impact:** This is a real, meaningful gap for a research tool whose whole premise is transparency and reproducibility. A researcher currently has no way to:
- See the actual breadth of the literature search (43 papers considered vs. 3 discussed) — right now the UI implies the search was much narrower than it was.
- Browse abstracts/authors of papers that were searched but not cited, to catch something the LLM's summary may have missed or judged less relevant than the researcher would.
- Understand *how* the query evolved across rounds (the `literature.log` reasoning/decision/query trail is a genuinely interesting, currently-invisible part of the process).

**Proposed UX (not yet scoped/committed to an approach):**
- A "See full list of relevant papers" affordance under the Literature card/full page, opening a clean table (title, authors, abstract snippet, link) sourced from `papers_processed.log` — same spirit as the Analysis stage's plot grid ("+N more" pattern) but for papers instead of images.
- The table's "abstract" column should be a short truncated snippet (rough starting point: ~30 characters + an ellipsis), not the full abstract — 43 full abstracts in one table would be overwhelming. Full abstract text (if wanted at all) would only make sense behind a per-row expand/click-through, not in the table itself.
- A dedicated "Related Literature" section on `LiteratureFullPage.tsx`, distinct from the "Most Relevant Papers" comparison section already built — the comparison section stays reserved for the LLM's actual similarities/differences reasoning; a new section would show the broader searched corpus without fabricating similarities/differences for papers the LLM never actually compared against.
- Render it as a collapsible table (title / authors / truncated abstract / link) in **both** places: under the compact conversation-thread card (collapsed by default, given 43 rows) and on the full page — same underlying data/component in both, just with the full page defaulting more open. Same collapsible-table pattern in both spots rather than two different UIs for the same data.
- Possibly surface the round-by-round query trail from `literature.log` (Reason/Decision/Query per round) as an optional "How this was searched" expandable — real transparency into the adversarial-style novelty-checking loop, mirroring how Idea's maker/hater loop is already shown as a process, not just a final answer.

**Feasibility confirmed (2026-07-19):** parsing `.log` files the same way we parse `.md` files is not just possible, it's easier than what we already built for `literature.md`. `papers_processed.log`'s per-paper blocks are generated by plain Python string formatting straight from the Semantic Scholar API's JSON fields (`denario/langgraph_agents/literature.py`'s `semantic_scholar()` — `f"{n}. {title} ({year})\nAuthors: {authors}\nAbstract: {abstract}\nURL: {url}"`), not LLM freeform text — a fully deterministic, code-generated format, more reliable to parse than `literature.md`'s LLM prose was. `literature.log`'s per-round `Reason`/`Decision`/`Query` blocks are already valid JSON (the prompt instructs the LLM to respond in exactly that format), so those are close to schema-constrained already.

**Recommended approach (staged, not started):** same pattern already proven for `literature.json`/`results.json` — a `denario/papers_log_parser.py` on the backend, writing a `papers_processed.json` sidecar (and possibly a `literature_rounds.json` for the `literature.log` query trail), rather than a frontend parser. Keeps parsing logic in one testable place (Python) instead of duplicating regex logic in TypeScript, and the frontend just consumes structured data the same way it already does for the other stages.

**Not yet designed:**
- The exact `papers_processed.json` schema (likely just `papers: PaperEntry[]` with `title`/`authors`/`year`/`abstract`/`url`/`pdf`, mirroring `LiteraturePaper`'s shape).
- The collapsible-table component itself — whether it's a new shared component (reusable if a similar "browse N items" need shows up elsewhere) or Literature-specific.
- Whether full abstracts for 40+ papers belong inline in the conversation thread at all, or only in a dedicated full-page/modal view (likely the latter, for the same reason Analysis reserves its full report for the full page rather than the compact card) — the truncated-snippet approach above sidesteps this somewhat by keeping the thread's version compact regardless.

**Reference:** real example confirmed on project `90fa5f38-37fb-4cea-87ba-0f3bfbe7092f` — `input_files/literature.log` (309 lines, 3 search rounds) and `input_files/papers_processed.log` (246 lines, 43 numbered paper entries with real abstracts/authors/URLs), versus `literature.json`'s 3-paper comparison list.
